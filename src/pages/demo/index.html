Two computers, one request.

The full record of the first run between installed UCompute desktop apps on a Mac and a Windows laptop: the machines, what we did, what we measured, and what is still broken.

VerifiedExperimental

Recorded 19 October 2026 with development builds. Verified for these builds, this hardware and this network only. It is not an offer to download the builds, and no alpha or beta cohort has started.

What we did

  1. Paired through the two screens

    On the Mac: Peers, then Pair this device, which shows a six-digit code. On Windows: Peers, Nearby, not paired, Pair, the code, then Join. Both apps then listed the other as Connected, and both audit logs recorded pairing_succeeded at 03:39:18 UTC.

  2. Checked that a wrong code fails

    A wrong code entered in the real Windows app was refused with a plain message (screenshot). For this check the Windows app was driven through its WebView2 developer port, and the Mac's pairing window was opened through its daemon API.

  3. Allowed remote runs

    On Windows, a group called home with the Mac and “Members may run prompts” ticked, set in the app. The Mac's group was created through its daemon API, because the Mac window could not be clicked in that session.

  4. Ran prompts both ways

    Windows to Mac from the Windows Chat view; Mac to Windows through the Mac daemon's API, sending the same request its Chat view sends.

These runs also found and fixed three Windows defects: free disk space read as zero, GPU names cut at the first bracket, and a killed daemon leaving its engine running. The last is now handled with a Windows job object, so the engine ends with the daemon.

Open issues

Found in these runs and being fixed now. None is marked solved here until committed engineering evidence says so. The list is kept in the evidence file and docs/BLOCKERS.md.

  • Mac wording on Windows

    Windows shows “Run on: This Mac” and similar text, and defaults its own device name to “This Mac”.

  • Remote runs need a local model

    Chat stays disabled until a model is loaded on this machine, even when the request will run elsewhere.

  • Endless redials

    An unreachable paired device is redialled about every 35 seconds, forever, with an audit line each time.

  • Shutdown and stale records

    Quitting on Windows does not shut the daemon down gracefully, and discovery can keep stale entries.

  • Addresses after a network change

    The wrong advertised address can be chosen, and a paired device may not reconnect after its address changes.

  • Connection state is hard to see

    Discovery and connection progress need clearer display; “Last seen” does not advance while a connection stays up.

  • Pairing started on Windows

    Windows Firewall drops the pairing connection when the Windows machine opens the pairing window. Open it on the Mac and join from Windows instead.
