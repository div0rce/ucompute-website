Two computers, one request.

The full record of the first run between installed desktop apps (development builds) on a Mac and a Windows laptop: the machines, what we did, what we measured, and what is still broken.

VerifiedExperimental

Recorded 19 October 2026 with development builds. Verified for these builds, this hardware and this network only. It is not an offer to download the builds, and no alpha or beta cohort has started. This record uses the current names; the builds it describes carried the earlier name.{{claim:demo-2026-10-19}}{{claim:no-release}}

Every recorded run

The 19 October run is the demonstration. These are the two-machine runs behind it and since, each with development builds of the day: a Mac and a Windows laptop from 18 to 22 October, and the same Mac with a Linux desktop on 23 October.

  1. 18 October

    Campus Wi-Fi, background services only

    Two runs where the network blocks discovery. Pairing by address, remote runs in both directions, and revocation: the laptop was cut off 0.012 s after the Mac revoked it.{{claim:daemon-runs}}{{claim:revocation}}

  2. 19 October

    Phone hotspot, background services only

    Each device found the other within about a second. Remote runs both ways, and a revocation that closed the connection in 0.061 s.{{claim:discovery}}{{claim:revocation}}

  3. 19 October

    The desktop apps, paired through their windows

    The Windows app ran a prompt on the Mac. This is the run the rest of this page describes.{{claim:demo-2026-10-19}}

  4. 22 October

    Campus Wi-Fi, newer development builds

    Where a network blocks automatic discovery, paired devices can still connect by address, and an address alone is never trusted. On Windows, the app asked before letting paired devices through the firewall, and Windows asked for administrator approval; pairing started from Windows then succeeded. In a later run that day, through the daemons' local APIs, a revocation closed the connection in 0.053 s. All 22 October runs used development builds made before the latest fixes.{{claim:connect-at-address}}{{claim:firewall-consent}}{{claim:windows-pairing}}{{claim:revocation}}

  5. 23 October

    Home Wi-Fi, a Mac and a Linux desktop, builds with the fixes

    The first two-machine run of builds with the latest fixes, driven through the devices' background programs rather than app windows. The Linux side was a development build compiled from source, on the processor only. Pairing worked starting from either device. A revocation closed the connection in 0.002 s, and the next request was refused. When the Mac's app was stopped, the other side saw the connection go within 0.52 s, and the two reconnected within 3.8 s of a restart; the Mac closed its own connections as it stopped, so this does not measure a silent loss. Linux is a planned platform, not a supported one.{{claim:linux-run}}{{claim:revocation}}

What we did

  1. Paired through the two screens

    The Mac app showed a six-digit code; the Windows app found the Mac on the local network and joined with the code. Both apps then listed the other as connected, and both audit logs recorded pairing_succeeded at 03:39:18 UTC.

  2. Checked that a wrong code fails

    A wrong code entered in the real Windows app was refused with a plain message. For this check the code was typed into the Windows app by automation through its WebView2 developer port, not by hand, and the Mac's pairing window was opened through its local API.

  3. Allowed remote runs

    On Windows, a group with the Mac and “Members may run prompts” ticked, set in the app. The Mac's group was created through its local API, because the Mac window could not be clicked in that session.

  4. Ran prompts both ways

    Windows to Mac from the Windows app's chat; Mac to Windows through the Mac's local API rather than its app window.

The wrong-code resultThe Windows app refused the join with a plain message, “Pairing did not complete. Check the code and that both devices are on the same network, then try again.”, and the typed error pairing_failed. The Mac stayed paired from the successful attempt.{{claim:demo-2026-10-19}}

Open issues

Found in these runs. {{if:acceptance}}Fixes from the newer code have since run on the same two machines; each item says what changed.{{claim:acceptance-fixes}}{{else}}Some fixes were confirmed on the same two machines on 22 October 2026, one on a Mac on 21 October, and some between the Mac and a Linux computer on 23 October; others exist only in newer code and still wait for a retest with Windows. Each item says which, and nothing is marked solved without committed engineering evidence.{{/if}}{{claim:open-defects}}

  • Mac wording on Windows

    {{if:acceptance}}Fixed: the wording is platform-neutral, and each device takes its own computer name.{{claim:acceptance-fixes}}{{else}}Partly fixed. With development builds on 22 October 2026, each device showed its own computer name, and the Windows chat view used platform-neutral wording. The other Windows views have not been checked yet.{{claim:open-defects}}{{/if}}

  • Remote runs need a local model

    {{if:acceptance}}Fixed: Chat can send a request to a paired device without a model loaded locally.{{claim:acceptance-fixes}}{{else}}Chat stays disabled until a model is loaded on this machine, even when the request will run elsewhere. A fix exists in newer code but has not run on two machines yet.{{/if}}

  • Endless redials

    {{if:acceptance}}Fixed: an unreachable device no longer fills the audit log.{{claim:acceptance-fixes}}{{else}}Fixed on a Mac (development build, 21 October 2026) and on a Linux computer (23 October 2026): an unreachable device no longer filled the audit log. Not yet shown on Windows.{{claim:open-defects}}{{/if}}

  • Shutdown and stale records

    Quitting the Windows app now ends its service cleanly, and the other device sees it leave (development builds, 22 October 2026). Whether a device that crashed is still listed until its entry expires has not been validly checked.{{claim:open-defects}}

  • Addresses after a network change

    A paired device can be reconnected at its new address, even on a network that blocks discovery (development builds, 22 October 2026). What happens when a device switches network on its own has not been tested.{{claim:connect-at-address}}{{claim:open-defects}}

  • “Last seen” stood still

    Fixed: “Last seen” now advances while a connection stays up (development builds, October 2026).{{claim:open-defects}}

  • Chat header on the wrong device

    After a request ran on the Mac, the Windows chat header still named the laptop's own GPU above the reply. Not yet rechecked with a newer build.{{claim:open-defects}}

  • Plural wording

    {{if:acceptance}}Fixed: the app says “1 device”.{{claim:acceptance-fixes}}{{else}}The app said “1 devices”. A fix exists in newer code but has not run on two machines yet.{{/if}}

  • A wrong code typed by hand

    On 19 October the wrong code was entered by automation, and on 22 and 23 October wrong codes were refused through the local API. No one has yet typed a wrong code into an app.{{claim:open-defects}}

  • The Mac's side in its own window

    The Mac's group setting and its requests have so far gone through its local API, not its app window.{{claim:open-defects}}

  • Nearby devices on home Wi-Fi

    In the 23 October runs, the Mac's list of nearby devices once lacked the Linux computer for more than 15 seconds, and a freshly started Linux program first saw only link-local addresses for the Mac. Both are still open.{{claim:linux-run}}{{claim:open-defects}}

  • Pairing started on Windows

    Fixed: the Windows app now asks, with administrator approval, to let paired devices reach it on private networks, and pairing started on Windows succeeds (development build, 22 October 2026).{{claim:windows-pairing}}{{claim:firewall-consent}}
