Open by design, honest by rule.

License and source

The project lives at github.com/div0rce/common. Today that repository holds the license and the founding brief; the code, the specification and the evidence records are being prepared for publication there.

The code is Apache-2.0. Contributors keep ownership of their work and contribute under the same license. There is no copyright assignment and no extra contributor agreement.

How to contribute

Ground rules

  1. Real over fake. No mocked inference presented as real, no fabricated benchmark numbers, no feature marked done without evidence.
  2. Requirements are tracked. Every feature maps to a row in the requirements ledger, and status changes need evidence. The ledger validator must pass before a commit.
  3. Secure by default. No plaintext peer transport, no non-loopback default, nothing that sends prompts off the device without explicit consent.
  4. Licenses matter. Never copy code from GPL or AGPL projects. New dependencies must be permissively licensed and justified.

The development loop

cargo build
scripts/fetch-fixtures.sh                    # pinned engine and tiny fixtures into ./.common
COMMON_HOME=$PWD/.common cargo test          # includes real-inference tests
cargo clippy --all-targets -- -D warnings
cargo fmt --all
python3 scripts/validate_registry.py         # the requirements ledger must stay valid

Tests that need hardware the project doesn't have, such as a second machine or a particular GPU, are labelled in their names and skip with a message. Never make them pass by faking the hardware. Tests that run several daemons on one computer are labelled single-host and never count as two-machine evidence.

Good first contributions

A good first task links to a work package or requirement, touches a bounded set of files, comes with fixture instructions and has a reproducible acceptance check. Each pull request that changes behavior updates its contract, tests, ledger evidence and user instructions, and says what was verified on which hardware.

How decisions are made

  • The repository owner is the current decision and merge authority. The ledger names areas of responsibility; that is not a claim that a staffed team exists.
  • A maintainer reviews correctness, security, evidence and license impact before merging. Security and protocol changes need a reviewer other than their author.
  • Architectural changes are proposed as decision records. Unresolved objections are written into the record, and the owner decides with a stated rationale.
  • Bug reports are triaged by reproducible impact, not votes. The beta target is a first response within seven days, and the project will say so when volunteer capacity can't meet it.
  • The goal is at least two active maintainers who can each run a release. That has not been reached.

Keeping the protocol open

Independent clients and devices must remain possible without proprietary accounts or the official desktop app. Protocol and schema changes start as a decision record with compatibility and migration tests, and invite review from independent implementers.

Conformance test vectors will be published under the project's open license. A future extension registry will separate “compatible” from “security-approved”, and will never run an extension just because it is listed. Plain descriptive compatibility statements are preferred over certification claims that haven't passed conformance.

Reporting a security problem

Security problems can expose prompts, model files or your computer, so please report them privately.

  • A private reporting route will be listed here once it has been tested with a harmless report, as the security policy requires before any external beta. Until then, do not post a suspected vulnerability publicly.
  • Include the affected version or commit, platform, steps to reproduce, impact and any proof of concept.
  • Targets: acknowledgement within 7 days and an update at least every 14 days. These are volunteer targets, not a contracted service level.
  • Please allow 90 days before public disclosure unless we agree otherwise.

The project's own policy requires the private reporting route to be tested, and a responsible responder named, before any external beta.

Trust boundaries

A trusted device that serves your request sees what it processes; encrypted transport is not confidential execution. Same-user processes are inside today's local trust boundary. Engine supervision contains crashes but is not a sandbox. Public contribution and arbitrary downloaded programs remain disabled until their own gates pass. No security certification is claimed.

Code of conduct

Be respectful, assume good faith, and keep discussion about the work. Harassment, discrimination, personal attacks and sustained disruption are not tolerated in any project space. Maintainers may edit, remove or reject contributions and comments that break this, and may ban contributors for repeated or severe violations. A private route for conduct reports will be listed here once it has been tested.
