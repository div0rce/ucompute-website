Trusted devices

UCompute Mesh lets one computer send a whole request to another computer you have paired and allowed. It is experimental, off by default, and limited to devices on the same local network.

What it does not do yetOne request runs on one device. Mesh does not split a model across devices, and it does not connect devices across the internet.

Before you start

  • Install UCompute on both computers and put them on the same network. Home Wi-Fi and phone hotspots work. Campus and office networks often block the multicast traffic that discovery needs; on those, pair by address instead.
  • Peer traffic uses UDP port 8193 by default. On Windows, UCompute asks before it lets your paired devices reach it through the firewall, and the rule it adds covers only its own program, on private networks. Shown on one Windows 11 laptop with a development build; Windows asks for administrator approval. The network profile must be Private.{{claim:firewall-consent}} On a Mac, the firewall may block incoming connections from a newly built app; if the Mac cannot serve requests, allow the app there. That cause is suspected, not confirmed.
  • Read what the other device can see. When a paired device runs your request, it decrypts the prompt and runs the model on it in plain text. It can read, log or keep the prompt and the answer.

1. Turn on trusted devices

In the app, switch the privacy mode to trusted devices and acknowledge the disclosure. From the command line:

common privacy trusted-devices      # shows the disclosure and asks y/N; --yes accepts it
common privacy                      # shows the current mode

This also turns on peer networking. The public option exists in the app only as a disabled placeholder.

2. Start networking

In the app, switch networking on. A daemon you run yourself needs:

common serve --network --serve-peers   # both settings are saved, not just for this run

Use --serve-peers only on a computer that should run work for others.

3. Pair

Open the pairing window on one computer and join from the other. The window lasts 120 seconds, and more than five wrong codes within a minute lock it. Tested between one Apple M2 Mac and one Windows 11 laptop (Intel Arc 140V) on the same Wi-Fi network or phone hotspot, with development builds; pairing has been shown starting from either of the two. Pairing between two Macs is not yet shown to work.{{claim:mesh-pair-choose}}{{claim:windows-pairing}}

  1. On the first computer, start pairing. It shows a six-digit code, the address to dial and a QR payload.
  2. On the second computer, pick the first one from the devices found on the network, or join it by address. Enter the code.
  3. Both now list each other as paired and connected.
Pairing a Mac and a Windows PCPairing started on Windows needs the app's firewall consent step, which Windows asks an administrator to approve; it worked with a development build on 22 October 2026. With older builds, open the pairing window on the Mac and join from Windows.{{claim:firewall-consent}}{{claim:windows-pairing}}

From the command line:

common peers discover               # devices advertising nearby; untrusted until paired
common peers pair                   # first computer: shows the code and waits (Ctrl-C cancels)
common peers join 192.0.2.20:51234 123456   # second computer: pairing address and code
common peers list

4. Allow it in a group, on both computers

Pairing proves identity. It does not grant permission. A device can only run work for a device in the same group, and only what the group allows. Both computers check.

common groups create home --allow-remote
common groups add home 1a2b-3c4d-5e6f
common groups policy home --allow-remote=false   # take it back later

The app has the same switches for groups. The pooled-inference permission is reserved for pooling, which is planned and not started, and does nothing useful yet.

5. Run on the other device

In the app's chat, pick the paired device to run on. From the command line or your own code, where every response names the device that ran it:

common run qwen2.5-0.5b-instruct-q4_k_m --chat -p "Hello" --peer 1a2b-3c4d-5e6f

curl -s http://127.0.0.1:8192/v1/completions -H 'Content-Type: application/json' \
  -H 'X-Common-Target: peer:1a2b-3c4d-5e6f' \
  -d '{"model": "stories15M-q4_0", "prompt": "Once upon a time", "max_tokens": 32}'

The serving device needs the same model file, identified by SHA-256. If its copy differs it refuses with integrity_mismatch rather than running something else.

Remove or revoke a device

common peers rm 1a2b-3c4d-5e6f       # forget it; it may pair again later
common peers revoke 1a2b-3c4d-5e6f   # signed revocation; its key is refused from now on

Revoking closes every connection to the device, tells the devices that shared a group with it, and makes its key fail inside the encrypted handshake. In two-machine tests the revoked device was disconnected less than a tenth of a second after the revoke (0.012 s, 0.061 s and 0.053 s in three runs). Tested between one Apple M2 Mac and one Windows 11 laptop (Intel Arc 140V) on the same Wi-Fi network or phone hotspot, with development builds; pairing has been shown starting from either of the two. Pairing between two Macs is not yet shown to work.{{claim:revocation}}{{claim:mesh-pair-choose}}

See what happened

common audit --n 20                       # recent pairing, policy and remote-request events
common diagnostics --out diagnostics.json # a redacted bundle to attach to a bug report

Both sides audit each remote request with the same request id. Audit logs record each off-device request without the prompt or the response: ids, counts, codes and timings.
