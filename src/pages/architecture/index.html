How the pieces fit.

A small daemon runs on each device. Applications talk to it over a local HTTP API; it decides what is allowed, runs supported work on a pinned engine, and talks to paired devices over its own encrypted protocol. This page describes the code as committed at af3e37c.

The shape of the system

A local request

  1. The API checks the caller. It listens on 127.0.0.1; browser requests from origins outside a short allow-list are refused, bodies are capped at 2 MiB, and with an API key configured every route but /health needs it.
  2. Admission control holds a bounded number of generation slots and a bounded queue. When they are full the caller gets a typed overloaded error instead of a hang.
  3. The model manager re-verifies the model file's hash before every load and checks that it fits in memory.
  4. The engine runs as a supervised child process on loopback, never reachable from the network, and ends with the daemon.
  5. Tokens stream back as server-sent events. Prompts never appear in logs or metrics.

A request on a paired device

Experimental

A request with "target": "peer:<id or label>" runs whole on that device. Policy decides before admission, before any model load and before any network traffic. All of these must hold on the sending device:

  1. privacy mode is trusted_group, which requires acknowledging that the other device sees the prompt in plain text;
  2. peer networking is on;
  3. the device is paired and not revoked;
  4. a group contains it and allows remote inference.

The sender writes its audit entry before anything leaves; if it can't, nothing is sent. The serving device checks its own side again: networking and serving turned on, the sender paired and in a group that allows it there, quotas of 120 requests and 200,000 tokens a minute with four at once by default, and never its last engine slot. The model must match a known SHA-256; a different file is refused, never substituted. Every response and every streamed chunk names the target that ran it.

The protocol

Experimental

  • Transport: QUIC with TLS 1.3 only. Devices authenticate with raw Ed25519 public keys (RFC 7250), and the pinned-key check runs inside the handshake, including on session resumption.
  • Pairing: SPAKE2 with a six-digit code or a QR payload, bound to the TLS exporter so a relayed connection cannot complete it.
  • Discovery: signed mDNS adverts on the local network. A discovered device is only a label; trust comes from pairing.
  • Messages: bounded protobuf envelopes, described in proto/common/v1/control.proto, carrying signed capabilities and JSON generation requests and events.
  • Liveness: loss of a peer is noticed within a bound of about six seconds, followed by automatic reconnection.

The Rust code mirrors the schema by hand, and the only implementation is this one. Protocol compatibility negotiation is a verified requirement F-08-10; independent interoperability is not U-01 not started. Before any stable claim, the specification requires a complete written profile, published test vectors, and a separately built implementation that shares no networking code and still exchanges real work.

Trust boundaries, stated plainly

  • A device that serves your request sees the prompt and the answer. Encryption protects the network path, not the work from the device doing it.
  • Supervising the engine as a separate process contains crashes. It is not a sandbox for untrusted code, and no arbitrary programs can be submitted.
  • Other processes running as the same user are inside today's local trust boundary.
  • Unix file permissions protect keys on macOS. Equivalent Windows protection has not been verified yet.
  • Builds are not yet signed by a publicly trusted identity. A checksum is not a signature.

Security policy

What comes next

Pooling (M4) starts with a static split of a model's layers across two physical machines over the existing encrypted connection, measured for correctness, memory, and the real network traffic per token.

Scheduling (M5) starts deterministic: filter out anything that breaks privacy, memory, quota or spend limits, then compare local and remote choices, and decline to distribute work when the overhead outweighs the benefit.

A workload contract will wrap today's inference requests in a versioned envelope that declares inputs, pinned runtime, resources, permissions and privacy. Unknown kinds of work are refused before anything starts.
